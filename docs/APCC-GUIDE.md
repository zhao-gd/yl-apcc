# APCC — Agentic PR/CI/CD 实践指南

> AI-native SDLC（AI 原生软件开发生命周期）的可落地方案。
> 一套让「五个 AI 角色」围绕 Git 单一事实源，把代码从 issue 一路推到合并的机制。
>
> 状态：v0.1（仍在打磨，欢迎共建）｜License：Apache 2.0

---

## 0. 一句话

**把「规划 / 开发 / 测试 / 运维 / 发布」拆成五个角色（preset），围绕 Git 单一事实源，把一条 issue 从「定案」自动流转到「合并」，并靠「验收硬阈值 + SSH 签名 + 分支保护」兜底质量。**

---

## 1. 背景：AI 写代码之后，新问题出现了

AI 能写代码了，但「AI 写的代码能不能上生产」成了新问题。三个具体痛点：

1. **单人 AI 万能但不可信**：一个通用 agent 既规划又开发又测试，没有对抗、没有制衡，出错没人拦。
2. **有 CI 但拦不住 AI 的错**：传统 CI 只查「语法/单测/格式」，拦不住「AI 把明文密码 base64 写进脚本」「AI 打 label 用了不存在的字段」这类**语义级错误**。
3. **流程散落、无版本、不可复用**：约定写在聊天里、脚本散在各处、踩坑经验随对话消失，换个项目全得重来。

APCC 是对这三个问题的系统性回答。

---

## 2. 方法论：五根支柱

### 支柱一：角色化（对抗式分工）

**理念**：把一个「万能 agent」拆成多个**角色**，用职责边界制造对抗。

先说清一个概念：这里的「角色」是 **preset**——在 dsh 框架里，一个 preset 定义了一个角色「你是谁、你看见什么、你能用什么工具」。五个 preset = 五个角色，它们**不是五个独立运行的实体**，而是同一框架下、通过不同 preset 让 agent 扮演不同角色，共享同一套基础设施。

| 角色（preset） | 职责 | 红线（不能做的） |
|---|---|---|
| **planner 规划** | 读 issue → 拆计划 → 评论到 issue | 不写业务代码、不 merge、不关 issue |
| **dev 开发** | 写代码、提 PR | 不 merge main、不关 issue |
| **tester 测试** | 验收、合并、关 issue | 不未经验收直接合并 |
| **ops 运维** | 盯执行、巡检、基础设施 | 不写业务代码、不部署 |
| **releaser 发布** | 打 tag、部署、回滚 | 不 merge PR、不写业务代码 |

**为什么对抗有效？** 规划、开发、测试是三种不同的思维。单 agent 从头做到尾，会陷入确认偏误（confirmation bias）——它写出来的东西，它自己「验收」时倾向于说「对」。把「写代码的」和「验收代码的」拆成两个角色，「写的人」不知道「验的人」会从哪个角度挑刺，才能逼出质量。

**权力制衡是角色化的核心**：merge 权唯一（tester）、关 issue 权唯一（tester）、部署权唯一（releaser）。权力不重叠，任何一环出错必有一环拦住。

### 支柱二：两阶段工作流（人在环中，且只在方向决策点）

**理念**：不是所有环节都自动化，人在「方向决策点」介入。

```
阶段一【讨论】planner 出方案 + dev/tester 参与挑战 —— 人主导，不自动化
        ↓ 用户拍板「定案」
阶段二【执行】dev 开发 → tester 验收 → 合并 —— 才自动化
        ↓
阶段三【冒烟】用户以最终用户身份手动测一次 —— 必须人做
```

**为什么讨论不自动化？** 自动化链条里，保障开发方向正确是第一步——方向错了就自动化，等于用最快的速度把错的东西堆起来（补丁摞补丁）。

这是「Human-in-the-loop」的**精确定位**：不是每一步都人审（那样失去自动化价值），而是只在**方向决策点**（定案）和**最终验收点**（冒烟）人审，中间的机械执行（开发、测试、合并）交给自动化。

### 支柱三：事实源唯一（外化记忆）

**理念**：一切状态落 Git，不落聊天、不落 AI 记忆。

- **Git 是唯一事实源**：issue / PR / label / review / comment 全部落 Git。
- **记忆长在 Git 里**（共享、可审计、持久），**不长在 session 里**（私有、易污染、会丢）。

**失忆 vs 长期 session 的取舍**：多 agent 接力场景下，「每次从事实源拉最新状态」优于「每个 agent 记住自己的历史」。因为：

- 事实源唯一 → 任何角色任何时候拉取，拿到的是同一个真相，接力不会错位；
- 长期 session 记忆会各记各的、会过时、会被旧方案锚定（补丁摞补丁的温床）；
- 失忆逼角色每次重看事实，反而更严（「这个之前验过没问题」是长期记忆最容易漏掉 bug 的借口）。

**结论：记忆应该外化到 Git（共享、可审计、持久），而不是内化在某个 agent 的私有 session 里。**

### 支柱四：基础设施治理（Infrastructure governs execution）

**理念**：AI 只负责「意图」（要做什么），**基础设施负责「执行边界」**（不能做什么）。

**为什么？** AI 是非确定性的（同一个输入可能不同输出），不能作为质量兜底的最终防线；而机器门禁是确定性的，可以信赖。

| 手段 | 兜住什么 |
|---|---|
| **SSH 签名**（每角色独立 ed25519） | 杜绝「未签名 git 作者身份」冒充 |
| **分支保护**（main 禁直 push、merge 白名单） | 杜绝「越权合并」 |
| **验收硬阈值**（6 项，任一不过即打回） | 杜绝「CI 绿但语义错」漏网 |
| **返工上限**（≥3 停自动） | 杜绝「无限辩论 / 补丁摞补丁」 |

一句话：**Agents orchestrate intent, Infrastructure governs execution。**

### 支柱五：框架 / 项目分层（约定优于配置）

**理念**：机制（框架）与经验（配置）分离，框架可升级、经验不丢。

```
框架层（APCC，跨项目通用，有版本，可升级）
  tools/ instructions/ presets/ gitea/ docs/
        ↓ install 时「框架打底」
项目层（每项目一份，独立演进，升级不碰）
  accept.yaml pitfalls.md regression.md
```

这正是「约定优于配置 + 覆盖（override）」：框架提供默认约定，项目用覆盖层定制。框架升级只动框架层，项目经验永久保留。

**这一层同时解决三件事**：复用（新项目只需写项目层）、经验保留（升级不覆盖项目层）、开源（框架层开源、项目层私有）。

## 3. 架构总览

```
┌─────────────────────────────────────────────────────┐
│  触发链（无常驻进程，靠一句话驱动）                    │
│  planner 打「已定案」→ 用户对 ops 说「#N 盯它完成」   │
│  → ops 用 goal 驱动 dev→tester→合并→完成             │
└─────────────────────────────────────────────────────┘
                    │
                    ▼
        ┌───────────────────────┐
        │   Git 单一事实源       │  issue / PR / label / review
        │  （Gitea/GitHub 等）   │  ← 唯一的真相
        └───────────────────────┘
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   planner       dev         tester      （角色化 agent）
   出方案        写代码       验收合并
```

## 4. 工作流与状态机

### 4.1 issue 生命周期

```
issue 创建（intent）
  →「讨论中」：planner 出方案，dev/tester 挑战，收敛
  →「已定案」：用户拍板，planner 打 label ← 自动化的起点
  →「待测试」：dev 开发完提 PR，打 label
  →「完成」：tester 验收通过，合并 + 关 issue
  （不通过 →「返工中/返工N」→ dev 改 → 回「待测试」）
```

### 4.2 返工上限

同一 issue 返工 ≥ 3 轮 → 停自动 + 打「需人工」+ 告警。

### 4.3 盯执行（ops 的 goal 驱动）

用户说「#N 已定案，盯它完成」后，ops 建一个 goal：

```
每轮 goal round：
  查 issue #N 的 label
  「已定案」→ 触发 dev 开发
  「待测试」→ 触发 tester 验收
  「返工中」→ 触发 dev 修改
  「完成」→ goal complete，汇报
  返工≥3 / 异常 → 停下，汇报用户
```

**不设常驻 cron 进程**——靠 goal 驱动，用户一句话启动，做完即停。

## 5. 验收硬阈值（6 项，任一不过即打回）

| # | 验收项 | 怎么验 | 通过标准 |
|---|---|---|---|
| 1 | 功能满足 | 对照 PR 正文「done 定义」逐条验证 | 逐条满足无遗漏 |
| 2 | CI 门禁 | 查 PR check status | 绿 |
| 3 | 回归不破 | 跑受影响的主流程/测试 | 无新增回归 |
| 4 | 测试覆盖 | pytest + 端到端 | 全绿无跳过 |
| 5 | 凭证安全 | 扫描（含 base64 形态） | 无泄漏 |
| 6 | 提交规范 | 看 author + message | 签名身份 + Refs 关联 |

**验收结论落盘到 Git（PR review + issue 评论），不落聊天、不落日志。**

## 6. 经验管理：分三路（不是所有经验都进 CI）

| 经验类型 | 例子 | 归宿 |
|---|---|---|
| **可自动化验证的** | 要回归的 bug、凭证 base64 要扫 | **CI 门禁**（回归测试 + 扫描规则） |
| **需 agent 读懂的** | 「打 label 要用专用端点」「动契约要 owner 审批」 | **项目 pitfalls + 验收规则** |
| **通用方法论** | 别信未签名作者、多 agent 协作税 | **知识库**（全局可检索） |

**经验只有「外化」了才算积累**——写下来、可检索、能被下一个 agent 读到。

## 7. 落地清单（可操作）

### 7.1 工具

| 工具 | 作用 |
|---|---|
| `trigger_role.sh <角色> <任务>` | headless 触发某角色执行一次性任务 |
| `scheduler_status.py` | 一屏看所有 issue 的状态机进度 |
| `yl-commit <账号> <msg>` | SSH 签名提交（自动带身份 + ed25519 签名） |
| `install.sh` | 幂等部署框架 + 项目覆盖 |

### 7.2 幂等 install（核心）

```bash
# install.sh 的六件事，每件都可重复跑：
① 部署 tools/ 到项目 scripts/        # 覆盖式 + 路径替换
② 部署 instructions/ 到项目根         # 覆盖式
③ 部署 presets/ 到 agent home         # 覆盖式
④ 应用项目层 projects/<项目>/         # 覆盖框架默认
⑤ Git 平台 label 幂等创建             # 查存在→跳过，缺失→创建
⑥ 密钥检查                           # 存在→跳过，缺失→提示
```

### 7.3 签名密钥

每个角色一对 ed25519，公钥录入 Git 平台并标记 verified，私钥走独立 keygen（**不进版本库**）。

## 8. 踩坑记录（pitfalls，随框架版本走）

> 这些是真实踩过的坑，不写下来下一个 agent 会再踩一遍。

### Git 平台 API 坑
- 某些版本 `PATCH /issues/{n}` 的 body **没有 labels 字段**，打 label 必须用 `POST /issues/{n}/labels`（增）+ `DELETE /issues/{n}/labels/{id}`（删）。改前先查 swagger。

### 凭证扫描坑
- CI 关键词扫描（password/secret/token）**匹配不到 `user:password` 内联形态**，base64 编码的明文会漏过。要额外扫 base64 形态 + 检查内联 `user:pass@host`。

### agent headless 坑
- 临时切全局 default preset 触发角色后，trap 恢复可能失效，**残留成某角色**。触发后要显式校验 default 是否恢复。
- headless 输出会被 telemetry 污染，headless profile 要关掉 telemetry。

### 权限坑
- 角色要改 issue label，需要该角色在 Git 平台有 `issues: write` 权限（默认 read 会 403）。

### 落盘错配坑
- 业务角色的落盘工具别给职能角色用（会把 CI 记录串到业务日志）。职能角色的结论落 Git（PR review + issue 评论）。

### 效率坑
- 盯执行别用 `sleep + 轮询`（busy-polling），要用 job 完成通知 / 事件驱动。同一个 job 被 poll 上百次是反模式。

## 9. 社区经验对照（我们的选择）

| 社区经验 | APCC 的应对 |
|---|---|
| 别信未签名 git 作者身份 | 每角色独立 ed25519 SSH 签名 + verified |
| AI 评审非确定性 | 6 项硬阈值 + 返工上限，机器兜底 |
| 多 agent 协作税 3~5× token | 角色化 + 单一事实源，减少来回 |
| 状态覆写 / 无限辩论 | merge/关 issue 权唯一 + 返工上限 3 |
| Agents orchestrate intent, Infrastructure governs execution | Git 作唯一事实源 + 分支保护 + 签名 |

## 10. 开源与版本

- **开源内容**：框架层 + 方法论（本文档）+ 一个脱敏的最小可跑示例。
- **不开源**：项目层（各项目私有经验）。
- **License**：Apache 2.0。
- **版本**：semver（v0.1.0 → v0.2.0），每次改流程/验收项/角色 → 升版本 + CHANGELOG。
- **定位**：「基于 [DeepSeek Harness](https://github.com/deepseek-ai) 的 Agentic PR/CI 实践框架」——dsh 给「agent 怎么跑」，APCC 给「多个角色怎么协同把代码推到合并」。

## 11. 未来演进

1. **工具一等化**：把高频脚本（trigger_role/scheduler_status）注册成 agent 的一等工具，而非 bash 内联调用。
2. **自举**：机制稳定后，APCC 用 APCC 流程管理自己的演进。
3. **事件驱动**：用 job 通知/webhook 替代轮询式盯执行。
4. **跨平台**：Git 平台抽象层，从 Gitea 扩展到 GitHub/GitLab。
